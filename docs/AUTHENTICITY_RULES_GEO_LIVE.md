## 1. Anti-counterfeit / hologram reader

DexForge should treat authenticity as a multi-signal evidence problem rather than a single camera guess.

Recommended capture sequence:
1. front still image
2. back still image
3. short multi-angle tilt video under controlled white light
4. optional UV/near-UV capture where suitable hardware exists
5. macro edge/corner capture
6. optional weight/thickness measurement from a Raspberry Pi grading dock

Signals can include:
- holographic/foil motion signature across a tilt sequence
- print registration/alignment
- microprint/text sharpness
- edge core/layer appearance
- colour/ink response
- UV response where a trusted reference exists
- card dimensions, thickness and weight
- set/printing-specific geometry

The result must be stated as counterfeit risk + confidence, never a guarantee of authenticity. Borderless/full-art/reverse-holo and different printing eras require separate reference templates.

### Provenance passport

After a trusted scan, DexForge can issue a local provenance-passport ID that links:
- exact printing identity
- scan timestamp
- image hashes
- defect/grade measurements
- authenticity observations
- ownership-transfer history
- marketplace listing/swap history

The passport is evidence of DexForge history, not proof that an unverified physical card can never be substituted later. For high-value trades, re-scan at each transfer.

## 2. Full and current rules

DexForge should not hard-code a permanently frozen rules copy. Maintain a versioned rules manifest containing:
- official source URL
- effective date
- retrieved timestamp
- document/content hash
- ruleset format/version
- superseded version link

Competitive/tournament play must verify the active official rules source before use. Changes should be diffed, reviewed and covered by regression tests before the engine marks a new ruleset current.

## 3. Bluetooth local play + server play

Two supported multiplayer modes:

### Bluetooth local
- native mobile app discovers/links a nearby friend using Bluetooth/BLE
- backend supplies the same rules/state schema used online
- local play can continue without internet once required card/rules data is cached
- do not put payment/auth secrets over the BLE game channel

### Server authoritative
- Render/DexForge server owns authoritative match state
- clients submit signed/validated actions
- server resolves turn order/rules and broadcasts updated state
- reconnect/resume and spectator modes can be added later

The same AR scene can attach to either transport.

## 4. Geo-adaptive AR

A DexForge AR scene can anchor to any valid latitude/longitude supplied with user permission. The app should adapt encounter/tabletop/gallery content to the user's real location without pretending that invented objects are official Pokémon GO spawns.

Use device GNSS/GPS/network location. Satellite-map layers, if shown, come from a licensed map imagery provider and should not be described as a live satellite camera feed.

Possible geo modes:
- park/walking AR encounters generated by DexForge
- local league/store event overlays
- collection galleries anchored at a chosen location
- Bluetooth friend battle anchored to the shared physical table/space
- server-hosted AR tournament rooms
- travel Pokédex: region/location contextual information

## 5. Pokémon GO real-time companion boundary

DexForge may combine real-time device position with legitimate public/current signals such as:
- official public Pokémon GO event/news information when available
- user-entered observations
- consented community observations
- local route/activity data

DexForge must not rely on undocumented private Pokémon GO gameplay/account endpoints, location spoofing, automated catching, or account automation.

If a future official gameplay/account API becomes available, add it through a versioned provider connector rather than changing the canonical DexForge contracts.

## 6. High-value next ideas

### Smart trade protection
Require both parties to re-scan high-value cards before and after a swap. Compare the physical fingerprint/defect map to the passport and flag possible substitution.

### Tamper-evident scan seal
Hash the normalized scan package and store the hash in the transaction audit record. This makes later image/file alteration detectable.

### Trusted grading dock
Raspberry Pi + fixed camera + diffuse multi-angle LEDs + optional UV LED + calibrated scale/thickness sensor. Repeatable lighting makes holographic-motion and defect comparison far more useful than uncontrolled phone photos.

### Collection twin
Every physical card gets a digital twin carrying its printing, condition, scans, passport, owner history, deck membership, swap state and AR model.

### AR trade table
Two nearby phones detect the same table/anchor. Each player places digital representations of proposed cards on the table, rotates/zooms them, views scan/grade/passport evidence and confirms the exchange.

### Anti-switch handover
Generate a one-time QR/NFC handover token for an accepted swap. Both users scan the token and the card before ownership transfer closes.

### Rules laboratory
Replay saved matches automatically against a newly imported ruleset to detect whether a rules update changes previous engine outcomes.

### Offline tournament box
A Raspberry Pi becomes a local LAN tournament server for venues with weak internet: pairings, deck lists, local matches, AR table anchors and later sync to cloud when connected.

### Accessibility layer
Voice card reading, large-text rules, colour-independent type cues, haptic turn prompts and spoken attack/effect resolution.
